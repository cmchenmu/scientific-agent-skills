# 第十章使用教学：可恢复的论文工作流

第十章将论文生成实现为一个持久化状态机，而不是让 Agent 无限检索、改写和调用工具。工作流只使用第七、八章中已经入库且对当前用户授权的 chunks；它不会自行下载文献、捏造 DOI 或在人工审核前导出最终稿。

## 1. 状态机

当前实现严格遵循以下路径：

```text
draft -> search_plan_review -> retrieve -> ingest -> relevance_review
-> evidence_table -> manuscript_draft -> human_review -> completed / failed / cancelled
```

状态、预算、搜索策略、checkpoint、相关性卡片、证据表和草稿都存储在 `data/workflows/manuscript_workflows.sqlite3`。重启 Python 进程后，`resume(workflow_id)` 会从数据库返回最后一个状态。

实现文件：

| 文件 | 作用 |
| --- | --- |
| [manuscript_workflow.py](../app/services/manuscript_workflow.py) | 状态机、持久化 checkpoint、预算、相关性卡片、证据表和草稿。 |
| [cli.py](../app/cli.py) | `workflow create`、`workflow plan`、`workflow advance`。 |
| [test_manuscript_workflow.py](../tests/test_manuscript_workflow.py) | 转换、checkpoint、人工审核和预算耗尽测试。 |

## 2. 前置条件

先完成第七章和第八章，在本地归档中准备一个已授权项目、文档和用户角色：

```bash
cd /GIT/scientific-agent-skills/lab-agent

uv run --no-sync python -m app.cli local ingest \
  --archive data/local-archive \
  --project mouse-neuro-demo \
  --source data/demo/tissue-sop.html \
  --classification internal-research \
  --allowed-role student

uv run --no-sync python -m app.cli local grant-role \
  --archive data/local-archive \
  --user-id student-demo \
  --project mouse-neuro-demo \
  --role student
```

`student-demo` 是教学用户。生产环境应从已认证的 OIDC subject 得到 `user_id`，且项目角色仅由管理员或受控同步服务写入。

## 3. 创建与审核检索策略

创建工作流会生成一个 UUID 并进入 `draft`：

```bash
WORKFLOW_ID=$(uv run --no-sync python -m app.cli workflow create \
  --root data/workflows \
  --archive data/local-archive \
  --user-id student-demo \
  --project mouse-neuro-demo \
  --question '组织固定前应如何保存？')
printf '%s\n' "$WORKFLOW_ID"
```

提交检索计划。计划必须包含 query、sources、inclusion 和 exclusion；CLI 本地模式的来源固定为 `local`：

```bash
uv run --no-sync python -m app.cli workflow plan \
  --root data/workflows \
  --archive data/local-archive \
  --workflow-id "$WORKFLOW_ID" \
  --query '组织 保存 固定' \
  --inclusion '已授权的项目文档' \
  --exclusion '无来源或无 ACL 文档'
```

此时状态为 `search_plan_review`。导师或 PI 必须先审核计划，才可检索：

```bash
uv run --no-sync python -m app.cli workflow advance \
  --root data/workflows \
  --archive data/local-archive \
  --workflow-id "$WORKFLOW_ID" \
  --action approve-plan \
  --reviewer pi-demo
```

没有审核而直接执行 `retrieve` 会因状态不匹配失败。

## 4. 执行受控步骤

每条命令只推进一个状态，便于观察、暂停、重试和审计：

```bash
uv run --no-sync python -m app.cli workflow advance --root data/workflows --archive data/local-archive --workflow-id "$WORKFLOW_ID" --action retrieve
uv run --no-sync python -m app.cli workflow advance --root data/workflows --archive data/local-archive --workflow-id "$WORKFLOW_ID" --action ingest
uv run --no-sync python -m app.cli workflow advance --root data/workflows --archive data/local-archive --workflow-id "$WORKFLOW_ID" --action cards
uv run --no-sync python -m app.cli workflow advance --root data/workflows --archive data/local-archive --workflow-id "$WORKFLOW_ID" --action evidence
uv run --no-sync python -m app.cli workflow advance --root data/workflows --archive data/local-archive --workflow-id "$WORKFLOW_ID" --action draft
```

各步骤含义：

| 状态 | 系统工作 | 安全边界 |
| --- | --- | --- |
| `retrieve` | 仅通过当前 `user_id` 的 ACL-first 检索找 chunks。 | 不会查询其他项目。 |
| `ingest` | 复用已检索的本地文档记录。 | 不下载新文献。 |
| `relevance_review` | 建立相关性卡片。 | 每张卡绑定 document/chunk。 |
| `evidence_table` | 建立 claim-evidence 行。 | 证据不能脱离原 chunk。 |
| `manuscript_draft` | 生成带可追溯证据列表的草稿。 | 无证据处保留 `TODO`。 |
| `human_review` | 等待人工检查。 | 不可自动导出为最终稿。 |

## 5. 相关性卡片与证据表

每个候选卡片包含：研究对象、模型、样本量、方法、主要结果、局限、与问题的关系和证据位置。当前确定性实现不会从原文猜测缺失信息；无法从 chunk 可靠得到的字段明确写为 `not reported`。

每个 evidence row 都保存：

```text
claim, document_id, chunk_id, evidence
```

JATS 文献的 DOI/PMID/PMCID 从入库阶段保留并可被卡片读取。工作流不会自行生成 DOI，避免出现虚构文献。

草稿中的证据行格式为：

```text
[document_id:chunk_id] 已授权的原文证据
```

背景、方法、结果和讨论中没有可支持来源的部分均为 `TODO`，必须由人工补全和核验。

## 6. 人工审核与终态

检查引用、原始数据、统计、作者贡献和局限性后，由人工审核人完成或拒绝：

```bash
uv run --no-sync python -m app.cli workflow advance \
  --root data/workflows \
  --archive data/local-archive \
  --workflow-id "$WORKFLOW_ID" \
  --action complete \
  --reviewer pi-demo \
  --approved
```

`--approved` 得到 `completed`；省略时得到 `failed`。用户也可在非终态时取消工作流。系统不提供跳过 `human_review` 的导出路径。

## 7. 预算和恢复

创建工作流时可设置 `--max-steps`。每次 `retrieve` 在调用前消耗一步；超过上限、token、成本或 deadline 后，工作流持久化为 `failed` 并记录 `budget_reason`，后续步骤不会继续执行。

因为每次状态转换都写 checkpoint，进程崩溃或重启后可使用 Python 服务层恢复：

```python
from pathlib import Path
from app.services.local_archive import LocalArchive
from app.services.manuscript_workflow import ManuscriptWorkflow

workflow = ManuscriptWorkflow(Path('data/workflows'), LocalArchive(Path('data/local-archive')))
print(workflow.resume(WORKFLOW_ID))
```

恢复只返回已持久化的状态，不会悄悄重复下载、入库或写入外部系统。

## 8. Agent 调用规则

Agent 不拥有任意状态迁移权限。服务端为它提供固定工具，并在每次调用前验证认证身份、项目、预算和状态：

```text
create_manuscript_workflow(authenticated_user_id, project_id, question)
submit_search_plan(workflow_id, structured_plan)
retrieve_authorized_evidence(workflow_id)
build_relevance_cards(workflow_id)
build_evidence_table(workflow_id)
draft_from_evidence(workflow_id)
```

Agent 可以起草检索策略和草稿，但不能：

- 代替 PI 审核检索计划；
- 下载受限或付费文献；
- 绕过 ACL 扩大项目范围；
- 伪造 DOI、文献卡片字段或引用；
- 将 `TODO` 变成没有来源的结论；
- 自动完成 `human_review`。
