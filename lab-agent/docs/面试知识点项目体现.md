# Lab Agent 面试知识点与项目体现

_*面向 AI Agent 工程师面试：将通用知识点映射到当前 Lab Agent 的真实实现，并持续追加后续问答。_

---

## Agent、聊天、RAG 与工作流的边界

**通用结论：** 聊天重生成；RAG 重检索证据；工作流重预定义步骤；Agent 允许模型在受控范围内选择工具或分支。固定流程优先工作流。

### 当前项目中的体现

| 概念 | 当前项目中的体现 | 是否依赖模型自主决策 |
| --- | --- | --- |
| 聊天 | 网页“知识问答”输入框与 `/v1/chat/stream` SSE 接口 | 交互层本身不等于 Agent；配置模型后，由受限 Agent 服务选择只读工具并返回带引用的总结。 |
| RAG | `LocalArchive` 与 `KnowledgeService`：解析、chunk、ACL-first 检索、hash-v1 向量/关键词排序、引用校验 | 否。它的职责是找已授权证据，回答只能引用本轮候选 chunk。 |
| 工作流 | `ManuscriptWorkflow` 的检索计划审核、证据表、草稿、人工审核状态机；`LocalAdminAdapter` 的 preview、审批、commit | 否。状态和转移由代码预定义，适合论文审核和报销等有合规步骤的任务。 |
| Agent | `AgentService` 通过模型 tool calling 在 `search_authorized_evidence`、`propose_literature_query` 两项服务端工具中选择 | 是，但仅在严格白名单内。模型不能调用导入、审批、提交或权限工具。 |

### 面试回答

> 这个项目里我没有把所有能力都叫 Agent。网页聊天只是交互层；RAG 是受 ACL 约束的证据检索能力；论文和报销属于步骤与审批固定的业务，所以我用显式状态机工作流实现。Agent 只负责低风险的研究辅助：配置模型后，它能在服务端限定的只读工具中选择检索已授权证据或生成候选检索式。
>
> 这体现了“固定流程优先工作流”：报销不能让模型决定是否跳过审批，论文审核不能让模型跳过人工复核；模型只适合处理方向理解、检索式生成和基于授权证据的总结。`AgentService` 的工具白名单不包含审批、提交、导入或权限判断；候选检索式仍须用户确认后，由独立的确定性导入接口执行。未配置模型时会降级为可审计的本地规则，不伪装成模型规划。

### 代码证据与边界

| 主题 | 代码或接口 | 需要如实说明的边界 |
| --- | --- | --- |
| 受限工具 Agent | `app/services/agent.py`、`/v1/agent/run` | 模型最多三轮工具调用；每次检索重新执行 ACL，引用只能来自本轮工具结果。 |
| RAG | `app/services/local_archive.py`、`app/services/knowledge.py` | 本地使用 SQLite 和 hash-v1 向量，是可复现 baseline，不是生产向量平台。 |
| 论文工作流 | `app/services/manuscript_workflow.py` | 是确定性状态机，有人工审核；不是模型自主规划。 |
| 报销流程 | `app/services/admin_adapter.py` | 是 SQLite 模拟器，未连接真实财务 API。 |
| 方向助手 | `app/services/agent.py`、`app/services/literature_import.py` | 模型只生成候选查询；实际导入必须经过单独的授权接口和用户确认。 |

### 追问与回答

1. 为什么报销不能交给自由规划 Agent？
   回答：报销会触发外部写入，正确顺序本身就是控制要求。模型可以协助填写草稿，但不能决定跳过金额策略、非申请人审批、`draft_hash` 一致性和幂等提交；这些门禁必须由 `LocalAdminAdapter` 执行。
2. 如果接入 LLM，模型可以访问哪些工具，哪些工具必须保留为确定性服务？
   回答：当前模型只可选择 `search_authorized_evidence` 和 `propose_literature_query`。ACL、角色判断、文献导入、论文状态推进、审批、提交、预算和审计都保留为服务端确定性能力。
3. 如何保证 RAG 的引用来自已授权证据，而不是模型伪造？
   回答：每次检索先由 `search_for_user()` 在 SQL 候选层过滤 ACL，再由服务端从结果构造 `Citation`，并以 `validate_citations()` 校验 `(document_id, chunk_id)` 属于本轮结果集。模型不能自行提供一个未经校验的引用 ID。
4. 论文工作流中，哪些节点必须有人类审批？
   回答：检索计划从 `search_plan_review` 进入 `retrieve` 前必须由 reviewer 批准，草稿从 `human_review` 进入 `completed` 前必须人工通过。模型最多协助候选检索或文本草稿，不能推进这些状态。
5. 如何将当前研究方向助手升级为真正的模型驱动工具选择，同时不扩大权限？
   回答：项目已采用这一方式：`AgentService` 用函数调用让模型在两个只读工具中选择，服务端仍重做参数、角色和 ACL 校验；候选检索式必须由用户发起独立导入请求才会写入知识库。

## 什么时候不该用 Agent

**通用结论：** 当步骤已经固定、结果需要严格复现、存在高风险外部写入，或模型没有带来有效决策增益时，不应把控制权交给自由规划 Agent。这类能力应由确定性服务、规则引擎或显式状态机执行；模型至多提出候选内容，不能绕过校验、权限和审批。

### 当前项目中的体现

| 场景 | 为什么不使用自由 Agent | 当前确定性实现 |
| --- | --- | --- |
| 报销审批与提交 | 提交会产生外部业务影响，必须防止超额、自己审批、草稿被篡改后继续提交和重复提交。模型不能决定是否跳过这些门禁。 | `LocalAdminAdapter` 先按策略生成 preview，再创建 `pending_approval` 任务；提交时校验精确的 `draft_hash`、非申请人审批和幂等键。当前是 SQLite 本地模拟器，不是真实财务 API。 |
| 论文撰写流程的状态流转 | 检索计划审核、证据核对和人工复核是合规与可追溯要求，不能让模型自行跳过。 | `ManuscriptWorkflow` 用显式状态机依次流转 `draft -> search_plan_review -> retrieve -> ingest -> relevance_review -> evidence_table -> manuscript_draft -> human_review -> completed`，并持久化 checkpoint、预算和截止时间约束。 |
| 权限与检索范围 | 用户能否读取某篇文献是安全规则，不是语言理解问题；模型不应根据提示词判断权限。 | `authz.py` 和 `LocalArchive` 在排序前执行 active user、项目角色和文档 ACL 判断，形成 ACL-first retrieval。 |
| 文献下载、解析与入库 | 这是典型 ETL：文件格式、体积、安全、去重、来源和授权状态必须一致、可审计、可重跑。 | `ingestion.py` 与 `LocalArchive` 固定执行类型/大小检查、可执行文件头拒绝、JATS 解析、SHA-256 和标识符去重、来源与许可证记录；开放获取导入只接受有全文的合规来源。 |
| 发布门禁与工具参数校验 | 路径穿越、Shell/SQL 片段和超长输入属于安全边界，不能由 Agent "酌情放行"。 | `release_gate.py` 以规则拒绝危险参数，并对审批草稿、checkpoint 和预算等条件进行确定性验证。 |

### 面试回答

> 在 Lab Agent 中，我刻意没有把所有流程都做成自由 Agent。凡是模型决策不会增加价值、但错误代价很高的地方，都写成确定性服务或状态机：报销提交需要策略校验、他人审批和幂等；论文工作流需要固定审核节点与 checkpoint；ACL 和文献入库则必须先保证权限、来源、去重和可复现性。
>
> 模型更适合处理低风险且不确定性高的部分，例如理解研究方向、生成候选检索式，或在已授权证据上做总结。项目现在提供了可选的 `AgentService`：配置模型后，它可在两项只读工具中选择；未配置模型时降级为可审计的术语映射或证据返回。无论哪种模式，服务端仍掌握权限判断、审批、提交、输入安全和审计，模型不能跳过这些门禁。

### 代码证据与真实边界

| 主题 | 代码或接口 | 面试中应强调的设计价值 |
| --- | --- | --- |
| 高风险写入 | `app/services/admin_adapter.py`、`app/services/release_gate.py` | preview、审批隔离、精确草稿校验和幂等，避免模型或重试导致错误提交。 |
| 固定流程 | `app/services/manuscript_workflow.py` | 显式状态、合法转移、checkpoint 与预算限制使流程可审计、可恢复。 |
| 权限边界 | `app/core/authz.py`、`app/services/local_archive.py` | 授权发生在检索与生成前；模型不拥有权限裁决权。 |
| 可复现入库 | `app/services/ingestion.py`、`app/services/literature_import.py` | 固定校验、哈希去重和来源记录使数据管道可重跑、可解释。 |
| 受限模型范围 | `app/services/agent.py` | 已有两工具、最多三轮的可选 tool calling；尚未接入真实外部财务系统、通用论文规划或统一模型成本审计。 |

### 追问与回答

1. 如果用户要求 Agent 直接提交报销，系统如何拒绝或降级为审批任务？
   回答：模型没有提交工具，服务端只接受报销草稿并走 preview -> pending approval -> approve -> confirm。即使用户在自然语言中要求直接提交，也不能越过该 API 状态机。
2. 为什么 ACL 必须在向量/关键词排序前执行，而不是把权限说明交给模型？
   回答：后过滤会让未授权文本进入召回、重排、缓存、日志甚至模型上下文，已经构成泄露。ACL-first 让未授权 chunk 根本不参与排序，模型也不需要、也不能判断权限。
3. 论文工作流中哪些状态允许模型辅助，哪些状态必须由服务端规则推进？
   回答：模型可辅助形成候选查询、总结已授权证据或草稿建议；`search_plan_review` 的批准、`retrieve` 后的入库、证据表门槛、`human_review` 与终态转换必须由工作流规则和人工动作推进。
4. 如何让 ETL 在失败后安全重跑，并避免重复入库或重复外部提交？
   回答：文献用 SHA-256 与文献标识符去重，并保存 manifest 和失败记录；报销用 idempotency key 绑定任务和外部请求，并在确认前校验审批和草稿 hash。重跑因而能识别既有结果，而非重复创建。
5. 接入 LLM 后，如何用工具白名单、参数校验和审计日志保持这些边界？
   回答：把工具 schema 固定在 `AgentService._tools()`，每次调用在 `_execute_tool()` 重新验证名称、长度、角色和 ACL，并只记录必要的调用摘要、结果 ID 与最终状态。模型输出永远不能直接作为权限或外部写入依据。

## 单 Agent、图工作流、多 Agent 如何选

**通用结论：** 默认先选单 Agent 或图工作流。任务只需要一次受控的理解、检索或总结时，单 Agent 的上下文和成本最简单；有审批、状态、重试、预算限制和人工接管时，用图工作流显式建模节点与转移。只有角色天然分工、各自产物可验证、且隔离上下文确有收益时，才引入多 Agent；否则会增加协调成本、状态不一致和调试难度。

### 当前项目中的体现

| 方案 | 当前项目采用情况 | 项目依据与取舍 |
| --- | --- | --- |
| 单 Agent | 已实现可选的受限 LLM 工具调用。 | `AgentService` 让一个模型在授权证据检索和候选检索式生成之间选择，最多三轮；它没有导入、审批、提交或权限工具，也不需要多个模型角色协作。 |
| 图工作流 | 已采用“图式状态机”思想，是项目处理复杂流程的主方案。 | `ManuscriptWorkflow` 定义固定状态和合法边：检索计划审核后才能检索，证据表后才能起草，最后必须人工审核。workflow、checkpoint、预算、deadline 与 `failed/cancelled` 终态被持久化，因此可恢复、可审计并能拒绝非法跳转。实现是自定义 SQLite 状态机，不是 LangGraph 等图编排框架。 |
| 多 Agent | 当前未实现，也不应为了“看起来更智能”而加入。 | 项目中的检索、入库、权限、审批和起草步骤存在严格前后依赖，并且核心产物必须落库、受 ACL 保护、可验证。拆成“检索 Agent、写作 Agent、审核 Agent”会引入上下文传递、证据一致性和权限扩散问题，但没有带来足够收益。 |
| 人类角色协作 | 已实现，但不是多 Agent。 | PI/reviewer 审核检索计划与论文，finance approver 审批报销；这是权限隔离的人机协作，决策主体是明确的人和确定性服务，而非多个模型实例。 |

### 面试回答

> 我在 Lab Agent 里没有默认上多 Agent。简单的研究方向导入和知识问答只需要受控检索与处理，单个受限执行单元就足够；真正复杂的是论文产出和报销审批，它们的难点是状态、审批、预算和审计，所以我用显式状态机建模成图式工作流。
>
> 例如论文流程必须从 `draft` 经检索计划审核、检索、入库、证据表、草稿到人工审核，代码只允许合法转移，并保存 checkpoint，以便失败后定位和恢复。项目当前没有 LangGraph 或多 Agent 编排框架，也没有并行分支；这是有意的范围控制。若未来需要多 Agent，我只会在角色边界天然清楚且输出能自动验证的场景引入，例如一个受限检索规划角色生成候选查询、一个证据校验角色验证引用；但二者都只能读取已授权内容，最终入库、审批和状态推进仍由确定性服务负责。

### 代码证据与真实边界

| 主题 | 代码或接口 | 面试中应强调的设计价值与边界 |
| --- | --- | --- |
| 图式状态和合法边 | `app/services/manuscript_workflow.py` 中的 `STATES`、`NEXT_STATE` 与 `_transition` | 状态与边由代码固定，能防止越级执行；它是图工作流思想的轻量实现，不是通用 DAG/图编排引擎。 |
| 审批节点 | `approve_search_plan()`、`complete_human_review()` | reviewer 必填，人工审核是显式节点，不是模型间“投票”。 |
| 可恢复与失败处理 | `checkpoints` 表、`resume()`、预算耗尽后的 `failed` 状态 | 每次状态推进持久化 checkpoint；当前实现强调恢复与审计，但没有声明通用自动重试编排。 |
| 单任务 Agent | `app/services/agent.py` | 模型可选择两项只读工具；它是受限单 Agent，不是拥有任意工具或工作流状态推进权的自主规划器。 |
| 多角色但非多 Agent | `app/services/admin_adapter.py`、`app/core/authz.py` | 申请人、审批人、PI 等是权限主体，不等同于多个 AI Agent。 |

### 追问与回答

1. 什么情况下应把当前状态机替换为 LangGraph 等图编排框架？
   回答：当任务出现大量动态分支、可恢复的并行子任务、跨节点共享状态、人工中断恢复或可视化编排需求，且自定义状态机维护成本超过框架收益时再引入。当前论文流程是短而稳定的线性依赖，自定义状态机更透明。
2. 多 Agent 的“角色分工”为什么不能只靠提示词约定，必须有工具权限与产物校验？
   回答：提示词不是安全边界，任何角色都可能被提示注入诱导越权。工具权限必须由服务端按身份发放，产物必须通过 schema、ACL、引用和状态校验，才能防止“角色”只是名称不同却能做同样危险的事。
3. 若检索规划和证据核验拆成两个 Agent，如何防止第二个 Agent 引用未授权或未检索到的资料？
   回答：第二个 Agent 只能接收第一个工具调用返回的 document/chunk ID 与文本，服务端再将其引用交给 `validate_citations()` 校验。它不能重新访问归档、构造任意 ID 或读取另一个项目。
4. 当前流程没有并行分支，哪些步骤未来可能安全并行，哪些必须保持串行？
   回答：不同独立来源的下载、解析和相关性卡片可在各自资源和预算内并行；检索计划审批、证据表定稿、人工审核、报销审批和外部提交必须串行，因为后一步依赖前一步的已批准版本。
5. checkpoint 和幂等键分别解决图工作流中的什么失败问题？
   回答：checkpoint 保存业务状态与已完成节点，支持崩溃后恢复和审计；幂等键保证一个有副作用的请求被重试时返回同一结果，而不是再次提交。两者互补，不能互相替代。

## ReAct 的优缺点

**通用结论：** ReAct 将“推理（Reason）-行动（Act）-观察（Observe）”串成闭环：模型根据当前信息选择工具，读取观察结果后继续调整，适合检索、排错和开放式探索。它的代价是模型可能重复调用、走偏或陷入长循环，轨迹更长、成本更高、结果也较难稳定复现。因此生产实现不能只靠提示词要求模型“谨慎”，而应把动作结构化、限制步数和预算、持久化状态与审计，并将危险操作交由确定性门禁处理。

### 当前项目中的体现

| ReAct 要素或风险 | 当前项目中的实现 | 应如实说明的边界 |
| --- | --- | --- |
| 推理-行动-观察的适用场景 | `AgentService` 已对研究方向与知识问题提供有限的 tool-calling 循环。 | 首轮强制请求已注册工具，后续最多两轮可继续调用或作答；这不是论文流程的自由 ReAct，也没有统一的模型成本计量。 |
| 结构化行动 | 论文流程被拆成 `set_search_plan`、`approve_search_plan`、`retrieve`、`ingest_retrieved`、`create_relevance_cards`、`build_evidence_table` 和 `draft_manuscript` 等显式服务动作。 | 这些动作由 CLI/API 或工作流调用，而非模型自行生成任意函数调用；这是未来接入 ReAct 时可复用的工具边界。 |
| 循环失控与成本 | `ManuscriptWorkflow` 的 `max_steps`、`max_tokens`、`max_cost_cents` 和 deadline 在每次受计量执行前检查，超限后进入 `failed`。 | 当前确定性流程里的 token/cost 增量为零，并未真实统计 LLM 调用费用；预算控制机制已经具备，但尚未接入模型计费数据。 |
| 轨迹难追踪、难恢复 | 每次状态推进写入 SQLite checkpoint；`GovernanceStore` 定义了 request/trace、工具、参数摘要、检索文档、耗时、成本和最终状态等审计字段。 | checkpoint 已用于论文工作流；治理存储是本地实现/契约，不能声称已覆盖所有网页请求或完整模型思维链。 |
| 危险行动与错误观察 | 检索始终 ACL-first，工具参数由 `validate_tool_arguments()` 做路径穿越、Shell/SQL 片段和大小校验；报销还要求审批与幂等提交。 | ReAct 即使将来接入，也只能请求这些受限工具，不能直接读越权数据、拼接命令或绕过审批。 |

### 面试回答

> ReAct 的优势是探索性强：模型可以先形成检索假设，调用工具观察结果，再决定下一步。它的问题也正来自这个循环，模型可能反复检索、错误地把一次观察当结论，导致轨迹变长、成本失控且不易复现。
>
> Lab Agent 已把有限的 ReAct 式工具调用用于低风险研究辅助：模型首轮必须请求已注册工具，之后最多再执行两轮，并只能选择已授权证据检索或候选检索式生成。论文流程仍将每一步固化为状态机，报销仍由确定性审批门禁处理。当前真实边界是模型调用尚未接入统一 token、成本、时延和审计计量；生产化前应补齐这些观测与预算，而不是扩大工具权限或循环次数。

### 追问与回答

1. 如何定义 ReAct 循环的停止条件，除步数和成本外还应考虑哪些信号？
   回答：还应设置无新增证据、重复工具参数、重复状态指纹、deadline、用户取消、权限拒绝和达到人工审批边界等停止条件。当前 Agent 用 `MAX_TOOL_ROUNDS = 3` 控制短循环，生产版应补齐这些统一信号。
2. 为什么不记录模型完整思维链，仍然如何保证可审计？
   回答：完整思维链既不稳定，也可能包含敏感上下文或不应持久化的中间内容。审计应记录模型/提示版本、允许工具、结构化参数摘要、授权证据 ID、工具结果、耗时、成本、拒绝原因和最终状态，这足以复现外部行为。
3. ReAct 观察到“没有结果”时，允许模型做哪些受限重试，何时应转人工？
   回答：可在上限内改写查询、缩小到已批准的同义词或请求用户澄清；不得扩大项目、来源、角色或预算。达到重试上限、连续无新增证据、涉及新来源或需要改变已批准论文计划时，应结束或转人工审批。
4. 如何避免模型把检索到的片段误当作已验证结论？
   回答：提示词把工具输出定义为不可信证据而非指令，回答必须附带服务端验证的引用；高影响结论还需证据表、来源质量规则和人工审核。检索命中只是支持材料，不等于事实已被独立验证。
5. token/cost 预算在调用真实模型、检索 API 和下载服务时应怎样统一计量？
   回答：为每次模型、检索和下载调用记录统一的 trace ID、输入/输出 token、供应商计费单位、延迟与估算成本，并在调用前检查全局和节点预算。计量失败应保守拒绝继续或进入人工处理，不能让成本变成无上限。

## planning 怎么落地

**通用结论：** Planning 不应只是模型输出的一段自然语言，而应成为可校验、可持久化的数据结构。至少要记录目标、子任务/依赖、允许使用的工具、成功条件、当前状态和预算。执行器根据计划和状态推进；当结果不满足成功条件时，可以生成新的候选计划，但固定子流程和高风险节点仍应由代码与审批门禁控制，不能每轮都让模型从头决定全部步骤。

### 当前项目中的体现

| planning 要素 | 当前项目实现 | 真实边界或改进方向 |
| --- | --- | --- |
| 目标 | `workflows.question` 保存用户的研究问题，`project_id` 和 `user_id` 固定了计划适用的项目和主体。 | 目标是持久化字段，但没有单独的 `goal` 对象、优先级或可量化验收指标。 |
| 计划数据结构 | `set_search_plan()` 接收并保存 JSON plan，强制包含 `query`、`sources`、`inclusion`、`exclusion` 四个字段，同时写入 checkpoint。 | 当前 plan 是最小检索计划，尚未拆为通用 task 列表，未显式声明每个节点的工具、输入/输出 schema。 |
| 依赖与状态 | `STATES` 和 `NEXT_STATE` 固定了 `draft -> search_plan_review -> retrieve -> ingest -> relevance_review -> evidence_table -> manuscript_draft -> human_review` 的前后依赖。 | 这是串行状态机，不是可动态扩展的任务 DAG；没有并行计划节点。 |
| 工具边界 | `retrieve()` 仅依据已审批的 `plan["query"]` 调用 `archive.search_for_user()`；方向导入则固定走受限 Europe PMC 开放获取下载和本地入库。 | plan 中 `sources` 当前仅由 CLI 固定为 `local`，没有模型可任意选择或调用的工具注册表。 |
| 成功条件与产物 | 无授权检索结果时无法入库；相关性卡片、证据表、草稿和人工批准分别是后续状态的前置产物。 | 成功条件分散在服务校验中，例如“有 retrieved evidence”“有 evidence rows”“人工批准”，尚未作为可配置字段写进 plan。 |
| 失败、重规划与恢复 | 超预算或超时会进入 `failed`，每一步写 checkpoint，可通过 `resume()` 获取持久化状态。 | 当前没有自动 replan：检索无结果会抛出错误，审核不通过则失败。合理升级方式是生成新 plan 版本，重新进入 `search_plan_review` 并再次人工审批，而不是静默改写已批准计划。 |

### 面试回答

> 我在 Lab Agent 中把 planning 落在可持久化的数据和状态机上，而不是让模型每轮重新思考流程。论文工作流创建时保存研究问题和预算；检索计划以 JSON 保存，至少包含 query、sources、inclusion、exclusion，并在进入检索前经过 reviewer 审批。后续检索、入库、证据表、草稿和人工审核由固定状态依赖推进，每一步都写 checkpoint。
>
> 成功条件也被落实为可验证产物：没有已授权检索结果就不能入库，没有证据行就不能起草，最终必须人工审核。当前没有自动重规划，这是有意保守的边界：无结果或审核失败不会让模型静默修改 query 继续跑。后续接入模型时，我会让模型只生成带版本号的候选计划，并附带目标、工具、成功条件和变更理由；系统将新计划送回 `search_plan_review`，审批后才允许替换执行。这兼顾了探索性、复现性和合规性。

### 追问与回答

1. 如果把计划升级为完整任务图，计划节点和边各应有哪些字段？
   回答：节点至少要有 ID、目标、输入/输出 schema、允许工具、数据分类、预算、超时、重试策略、成功条件和负责人；边要有依赖类型、传递的已验证产物 ID、触发条件、失败分支和是否需要审批。计划本身还应有版本、创建者和批准记录。
2. 为什么“检索无结果”不能直接由模型改写 query 并继续执行？
   回答：自动改写可能悄悄改变研究问题、扩大来源或消耗更多预算，导致已批准计划失去可追溯性。低风险问答可以有限重试；论文工作流应把新查询作为新计划版本送回 `search_plan_review`。
3. 新计划版本应如何关联旧计划、checkpoint、证据与审批记录？
   回答：新版本保存 `parent_plan_version`、变更理由、差异摘要和新审批 ID，旧版本与其 checkpoint 保持不可变。证据行同时记录产生它的计划版本和查询摘要，才能回放“哪份计划得到了哪条证据”。
4. 哪些成功条件应由代码验证，哪些可让模型作为软评分或建议？
   回答：权限、schema、状态转换、引用可访问性、预算、审批和外部提交结果必须由代码验证；相关性、摘要质量、查询候选和证据覆盖建议可由模型做软评分，但不能单独决定通过。
5. 如何避免一次重规划扩大数据访问范围、工具权限或成本预算？
   回答：新计划继承原计划的项目、角色、工具 allowlist、来源 allowlist 和预算上限，任何扩大都要求显式策略批准和人工审核。执行器不接受模型携带的权限字段，只从服务端上下文读取。

## Agent state 包含什么

**通用结论：** Agent state 是任务在可恢复执行过程中需要的最小、可信上下文，不等同于把所有数据都塞进一张表。应包含任务/用户/租户或项目标识、目标和计划、当前步骤及状态、受限工具调用和结果引用、审批决定、错误、预算、最终状态与 schema/计划版本。大文件、全文、附件和完整工具返回应放对象存储或业务库，state 仅保存不可变 ID、哈希、摘要和必要的定位信息；这样更利于恢复、审计、权限控制和成本管理。

### 当前项目中的体现

| state 要素 | 当前项目中的落点 | 真实边界或改进方向 |
| --- | --- | --- |
| 任务与主体标识 | `workflows.id` 是工作流 ID，表中保存 `user_id`、`project_id`、`question`；审批任务另有 `admin_tasks.id`、`requester_id`。 | 项目以 `project_id` 做隔离边界，未建模独立的 tenant ID；如走多租户部署，应增加 `tenant_id` 并加入全部查询、缓存和对象路径。 |
| 目标、计划与当前状态 | `question` 是研究目标，`search_plan` 保存 JSON 检索计划，`state` 保存当前节点，`STATES` 定义终态和中间态。 | `search_plan` 没有版本号或 schema version；计划修改、回退和重规划尚未实现。 |
| 步骤、预算与终止原因 | workflow 表记录 `steps`、`tokens`、`cost_cents`、三个上限、`deadline_epoch` 和 `budget_reason`；治理表也有相同预算字段。 | 当前确定性检索将 token/cost 以 0 计量，真实模型/API 调用尚未接入统一计量。 |

### 面试回答

> 在 Lab Agent 中，我把 state 分成三层。工作流 state 保存谁在什么项目下执行什么研究问题、当前在哪个节点、检索计划、步数/预算/截止时间和 checkpoint；证据 state 用 document ID、chunk ID、哈希和检索结果来连接文献库；高风险写入 state 则额外保存 draft hash、审批决定、幂等键和外部请求 ID。这样工作流可以恢复，审批和证据也能审计。
>
> 我不会把“state”理解为存全部原文。项目已经把原始文档放在对象目录，只在文档记录里保留 object key 和 SHA-256，并对审计 payload 做脱敏。不过当前教学实现仍将 chunk 正文、草稿正文，以及部分检索条目放入 SQLite/checkpoint，这不完全符合生产环境的最小 state 原则。生产化时我会把这些大内容迁到对象存储或受 ACL 保护的文档表，让 state 只保留版本、ID、摘要、哈希和可复现的查询参数；同时补齐 tenant ID、计划 schema/version 与统一错误码。

### 追问与回答

1. workflow state、业务数据、审计日志和对象存储分别应承担什么职责？
   回答：workflow state 保存当前节点、计划、预算和恢复所需的最小状态；业务数据保存文档、证据、任务和审批等权威记录；审计日志保存谁在何时为何执行了什么；对象存储保存原始文件和大对象。四者分离能控制体积、权限和保留策略。
2. 为什么 state 中要存 hash 和 ID，而不是只存文件路径或完整工具输出？
   回答：路径会迁移、可被替换且不表达内容版本；hash 能证明内容一致性，稳定 ID 能定位受 ACL 保护的资源。完整输出会膨胀 state 并扩大敏感数据暴露，应该存摘要、ID 与可复现参数。
3. 如何让 checkpoint 在重试后避免重复提交外部写入？
   回答：先在 checkpoint 记录请求意图、idempotency key 和状态，再调用外部系统；重试先查询已有 external request 或使用同一幂等键。只有确认没有既有成功或处理中请求时才能继续，不能只凭“上次超时”再次提交。
4. 多租户时 `tenant_id` 应在哪些表、缓存键、对象键和 API 过滤条件中出现？
   回答：它应出现在所有业务主表、关联表、审计表、工作流表、向量/全文索引、缓存键、对象存储前缀和每个 API 查询条件中。数据库约束和复合索引也应包含它，防止漏过滤造成跨租户读取。
5. state schema 和 plan version 如何支持迁移、回放与历史审计？
   回答：为 state 与 plan 保存显式 schema/version，迁移采用新增版本和纯函数转换，旧记录不可原地覆盖。回放时按原版本解释或迁移并记录转换链，审计保留原始版本、转换版本和操作者。

## 终止条件如何定义

**通用结论：** 终止条件应先定义为可观察的状态，而不是“模型说任务完成”。至少区分成功、失败、取消和预算耗尽；同时设置最大步骤、token/成本、deadline，以及针对 Agent 循环的重复 state/重复工具调用检测。成功必须由可验证产物和必要审批决定。终止原因、最后状态和证据应持久化，避免重试后继续错误执行或重复外部写入。

### 追问与回答

1. “任务完成”为什么不能只由模型返回 `done` 决定？
   回答：`done` 只是模型文本，不证明证据存在、审批完成或外部写入成功。完成条件应是可验证产物，例如有效 citation、完整证据表、已批准 reviewer 记录或外部系统回执。
2. 重复 state 检测的指纹应包含哪些字段，如何避免把正常重试误判为死循环？
   回答：指纹应包含规范化目标、计划版本、工具名、规范化参数、授权证据 ID 集合、状态和结果摘要，不应包含完整 prompt。相同幂等重试若有新的 attempt、退避窗口或外部状态变化应允许；连续相同指纹且无新证据才判为无进展。
3. 预算耗尽、工具暂时失败、无检索结果和人工拒绝应分别如何处理？
   回答：预算耗尽应硬停止并记录原因；暂时失败按有限退避和幂等策略重试；无结果应返回无证据或请求澄清，不能扩大权限；人工拒绝应终止当前版本并保留可审计理由，只有新计划才可重新开始。
4. 如何在取消请求到达时防止正在运行的外部写入继续提交？
   回答：执行器在每个可取消边界检查取消标志，并在外部调用前再次检查；取消与提交需要原子状态竞争控制。若请求已送达外部系统，改为查询最终状态和补偿流程，不能假设取消成功。
5. 成功验收怎样同时验证证据覆盖、引用可访问性和人工审批？
   回答：服务端验证每个关键结论至少关联合格证据，`validate_citations()` 验证引用属于授权集合且资源仍有效，工作流再检查证据表和审批状态。三项任一失败都不能进入最终完成态。

## 如何处理工具失败

**通用结论：** 先按失败类型分类，而不是笼统地“重试”。网络超时、临时 5xx 和限流可以在固定次数内退避重试；结构/schema 错误应返回机器可读错误，并只允许模型进行有限次结构化修正；权限拒绝、危险参数、审批冲突和重复外部写入属于不可重试或需人工处理的失败，必须直接停止。每个工具都应明确超时、重试次数/退避、幂等键、错误码、审计和最终状态。

### 追问与回答

1. 哪些 HTTP 状态码或网络异常适合重试，哪些不适合？
   回答：连接超时、DNS 临时失败、`408`、`429`、以及多数 `5xx` 可在幂等前提下重试；`400`、`401`、`403`、`404`、`409` 和 schema/业务策略错误通常不可盲目重试。`409` 应先查询当前资源状态再决定。
2. 如何实现指数退避、抖动和 `Retry-After`，同时避免重试风暴？
   回答：使用有最大次数和最大总时长的指数退避，在延迟上加随机抖动；服务端返回 `Retry-After` 时优先遵守其值。再按用户、项目和下游服务做并发/速率限制和熔断，防止大量任务同步重试。
3. 为什么 schema 修正只能允许有限次数，而不能让模型无限重试？
   回答：无限修正会掩盖工具契约错误、消耗成本并形成循环，还可能不断尝试越权字段。只对明确可修复的字段错误给出结构化反馈，并限制一到两次尝试，之后转人工或失败。
4. 外部提交超时后，如何通过幂等键和查询接口判断是否已经成功？
   回答：以同一 idempotency key 查询本地 `external_requests` 或外部提供方的状态；若存在成功回执则返回它，若处理中则继续等待或轮询，只有明确不存在时才安全重试。同一个 key 必须绑定同一规范化 payload。
5. 如何设计统一错误码，使前端、模型、审计和重试调度能使用同一分类？
   回答：响应统一包含 `code`、`message`、`retryable`、`trace_id`、`retry_after_seconds` 和可安全展示的字段错误；例如区分 `AUTHZ_DENIED`、`VALIDATION_FAILED`、`BUDGET_EXHAUSTED`、`UPSTREAM_TRANSIENT`、`CONFLICT`。HTTP 状态码负责传输语义，业务 code 负责稳定决策。

## 如何防止死循环

**通用结论：** 防止死循环必须依赖服务端状态和预算，不能仅靠提示词。至少包括全局步骤/token/成本上限、每个工具的重试上限、节点与工作流 deadline、状态或工具调用指纹、以及“无新增证据/无状态进展”的判定。超过任一上限时，必须写明停止原因并进入失败、等待澄清或人工接管；高风险外部写入还需幂等保证，避免重试变成重复执行。

> 在 Lab Agent 中，我先用确定性结构减少循环空间。论文流程不是自由回环，而是固定状态机；每一步要满足前置状态，状态转移会持久化 checkpoint。执行还受最大步骤、token、成本和全局 deadline 限制，超限时写入 `failed` 与具体 `budget_reason`，因此不是简单地停止而无法解释原因。对于有副作用的报销操作，再叠加 idempotency key、审批和草稿哈希，防止重试造成重复提交。
>
> 但我不会夸大当前能力：它尚未运行自由 ReAct 循环，所以没有同工具重试上限、state hash 或无进展检测。若接入 Agent，我会对 `workflow_id + node + tool_name + 规范化参数 + 上次结果哈希` 计算指纹，记录连续重复次数；相同调用超过上限，或连续 N 轮没有新增授权文档、证据行或状态变化时，停止并标记 `no_progress`，再要求用户澄清或转 reviewer。每个停止事件都写入 trace、预算快照、最后工具结果摘要和原因，便于恢复与排障。

### 追问与回答

1. state hash 应包含哪些信息，为什么不能直接 hash 完整原始 prompt？
   回答：应包含规范化意图、项目/计划版本、当前状态、工具名与参数摘要、授权证据 ID、预算桶和结果摘要。完整 prompt 可能含敏感信息、无关措辞和非确定性内容，会降低去重效果并把不必要内容纳入日志。
2. 如何定义“无进展”，并兼顾检索探索与避免过早终止？
   回答：无进展是连续调用得到相同或更差的状态指纹，且没有新增授权证据、候选查询、用户信息或业务状态变化。允许预先定义的不同查询分支有限探索，但每个分支都消耗预算并记录新增产物。
3. 全局预算、节点预算和工具重试次数发生冲突时，哪个优先？
   回答：任一硬上限触发都应停止，因此实际优先的是最先耗尽的限制；全局预算防止单任务失控，节点预算防止某一步吞噬全部资源，重试次数限制瞬态故障。策略应在调用前统一检查并记录触发原因。
4. 用户澄清、人工审核和自动重规划分别应该从什么状态恢复？
   回答：用户澄清应创建或更新待确认输入后回到相应的规划节点；人工审核通过后从被批准的下一状态继续，拒绝则终止该版本；自动重规划只能创建新计划版本并回到 `search_plan_review`，不能覆盖已批准状态。
5. 为什么幂等键不能替代重复 state 检测？
   回答：幂等键只处理同一外部副作用请求的重复投递，不能发现模型在不同参数、不同工具或不同节点之间来回循环。重复 state 检测关注任务是否产生新信息或推进状态，两者覆盖的问题不同。

## HITL 放在哪

**通用结论：** HITL（Human in the Loop）应放在不可逆、高影响或需要专业责任归属的边界之前，而不是把人工插在每个低风险步骤中。典型节点包括发送对外消息、创建正式工单、修改生产数据、支付/报销、删除和设备控制。审批界面或审批记录必须能让人看清：谁发起、参数是什么、影响范围、数据/证据来源、审批的具体版本、可选的批准/拒绝/取消动作，以及提交后的审计 ID。

### 面试回答

> 我把 HITL 放在影响边界，而不是每一次检索上。Lab Agent 中，检索计划必须先由 reviewer 批准才能执行；论文必须经过人工审核才能从 `human_review` 进入 `completed`；最典型的是报销，系统先生成 preview，再创建待审批任务，由具备 finance-approver 角色且不是申请人的人审批，最后才允许带幂等键的 confirm 提交。

### 追问与回答

1. 为什么“模型先生成、用户点击确认”仍不足以构成安全 HITL？
   回答：确认按钮只有在用户看到规范化参数、影响范围、证据来源、版本和明确后果，并且服务端将确认绑定到不可变对象时才有意义。若确认的是模型摘要、后台可替换 payload 或权限不受控的动作，它不能防止误导和 TOCTOU 问题。
2. `draft_hash` 如何防止审批后内容被替换，哪些字段必须参与哈希？
   回答：审批时对规范化 payload 计算 hash，提交时重新计算并要求完全一致；哈希应包含申请人、项目、金额、币种、收款/用途、收据、策略版本和会影响外部写入的全部字段。显示文本之外的隐藏参数也必须纳入。
3. 如何设计多级审批、金额阈值和职责分离，避免申请人自批？
   回答：按金额、风险类别和预算来源选择所需审批层级，要求审批人角色与申请人分离，并校验组织关系、审批有效期和顺序。每一级审批都绑定同一 draft hash，任何修改都使之前审批失效。
4. 文献入库何时需要二次审批，何时仅需角色授权即可？
   回答：低风险、开放获取、固定来源且数量/成本很小的入库可仅由 research-assistant 或 PI 角色授权；涉及受限版权、敏感数据、陌生来源、大批量/高成本或会影响正式结论的语料，应增加候选清单预览和第二人审批。
5. 人工拒绝、审批过期、撤销审批和外部提交已发生分别应如何处理？
   回答：拒绝和过期使当前 draft 不可提交，需修改后新建版本；撤销仅在外部提交前有效并写审计记录；外部提交已发生则查询回执，按外部系统的退款、冲销或补偿流程处理，不能假装“撤销成功”。

## 如何度量自治

**通用结论：** 自治程度不是“模型调用次数越少越高”，而是系统在授权范围内可靠完成任务，并在不该继续时安全停止。指标至少应同时覆盖：任务成功与质量、工具正确率、人工接管/审批、失败安全性、成本、时延和返工率。对高风险任务，正确拒绝越权、危险或证据不足请求同样是成功；必须把“安全拒绝”与“无理由失败”区分开来。

### 面试回答

> 我不会只用“任务完成率”衡量 Agent 自治。Lab Agent 把自治拆成任务质量、工具正确性、人机协作、安全、成本和时延六类信号。当前已经有约 30 个知识问答评测 case，覆盖授权、引用、无证据和攻击输入；发布检查还会验证路径穿越、SQL/Shell 片段、超额报销等是否被正确拒绝。这里的拒绝不是失败，而是高风险任务的正确结果。
>
> 对复杂任务，我把成功定义为可验证产物和必要审批：论文需要证据表、草稿和 reviewer 批准，报销需要合法 preview、独立审批和幂等提交。项目还预留了 trace、工具版本、时延、估算成本和最终状态字段。当前不足是这些数据没有统一自动采集和看板，发布报告也只检查评测数量而不计算成功率。因此生产化时我会按任务风险分组，监控任务成功率、工具调用正确率、人工接管率、拒绝的 precision/recall、p95 时延、每成功任务成本和返工率；当安全拒绝变差或 false allow 上升时，即使完成率高也要降级或回滚。

### 追问与回答

1. 为什么高风险任务应优先优化 false allow，而不是盲目提高完成率？
   回答：一次错误付款、越权读取或未经审核的论文结论造成的损失，通常远大于一次合理拒绝带来的人工成本。因此要同时看完成率和安全拒绝率，并把未授权放行、错误外部写入等 false allow 作为最高优先级事件。
2. 如何区分“合理拒绝”“工具故障”“模型错误”和“人工主动取消”？
   回答：为每次结束记录稳定 code 和责任层：策略/ACL 拒绝为 `AUTHZ_DENIED`，上游超时为 `UPSTREAM_TRANSIENT`，模型 schema 或引用失败为 `MODEL_OUTPUT_INVALID`，用户/审批人停止为 `CANCELLED_BY_HUMAN`。指标按 code 聚合，而不是只看 HTTP 是否成功。
3. 人工接管率高时，如何判断是模型能力不足、流程设计过严还是风险策略正确？
   回答：按任务风险、接管原因、证据质量、模型置信度、审批耗时和最终人工结论分层分析。低风险任务频繁因格式或简单检索接管说明模型/体验可改进；高风险写入的稳定人工审批则可能正是正确的策略。
4. 如何设计离线评测集、线上埋点和人工抽检，使三者互相校验？
   回答：离线集覆盖授权、无证据、提示注入、正常和边界任务，用于回归；线上埋点记录真实分布、模型/工具版本、延迟、成本和拒绝；人工抽检对高影响及随机样本判定质量。离线发现回归、线上发现漂移、抽检校准自动指标，三者互补。
5. 每成功任务成本应如何分摊检索、下载、模型、审批等待和重试成本？
   回答：以 trace ID 汇集直接 API/计算成本、下载流量与存储成本、重试成本和审批等待/人工时成本，再按最终成功任务数或业务单位分摊。报表应同时展示均值、p95 和失败任务消耗，不能只把成功任务的模型费用相除。

## 好工具接口的标准

**通用结论：** 好工具接口应做到单一职责、清晰且稳定的命名、严格的 JSON Schema、有限且有边界的参数、稳定错误码、机器可读返回，以及明确的副作用和权限标记。参数校验、授权、幂等和安全检查必须由服务端完成；模型只能提交结构化参数，不能自行拼接 Shell/SQL，也不能用自然语言绕过业务规则。

### 当前项目中的体现

| 接口标准 | 当前项目中的体现 | 真实边界或改进方向 |
| --- | --- | --- |
| 单一职责与命名 | API 将知识问答、受限 Agent、文献导入、方向导入、报销 preview/create/approve/confirm/cancel 分开；`AgentService._tools()` 只注册 `search_authorized_evidence` 与 `propose_literature_query`。 | 当前工具注册表只在该服务内，没有覆盖整个项目的统一 tool manifest；部分内部服务方法仍由 Python 类型和约定承载，而不是公开的 JSON Schema。 |
| 严格 Schema 与有限参数 | `app/main.py` 使用 Pydantic `Field` 限制项目 ID、问题长度、金额、币种、收据数量、导入数量和方向长度；审批 decision 使用正则限制为 `approved|rejected`。 | `set_search_plan()` 接受 `dict[str, Any]`，只检查四个字段存在；没有为 query/source/inclusion/exclusion 定义类型、长度和枚举的统一 schema。 |
| 服务端参数校验 | 报销还会检查字段集合、金额阈值、币种、描述和收据；`validate_tool_arguments()` 递归拒绝路径穿越、Shell/SQL 片段和超大结构化参数。 | API 的 `AdapterError` 多数统一映射为 403，schema 错误、权限错误和业务冲突尚未使用稳定、可分类的错误码。 |

| 副作用标记与分阶段提交 | 报销 `Preview.impact` 返回 `external_write: true`、金额和币种；流程拆成 preview -> pending approval -> approve -> confirm，避免模型直接执行外部写入。 | 其他会改变知识库的文献导入接口没有统一 `side_effects`/`dry_run` 字段，也没有先预览候选论文再确认的通用协议。 |
| 权限、来源和证据边界 | `can_execute_tool()` 按服务端用户/项目角色/允许工具判断；知识检索先 ACL；引用必须属于本轮授权 chunk。 | 本地开发身份由 `X-User-Id` 选择，非生产认证；工具权限仍需在真实 OIDC/策略系统中构造，不能信任客户端 roles。 |
| 幂等与版本一致性 | 报销创建和确认均需要 idempotency key，提交还匹配 `draft_hash`、审批人和审批有效期；文献以 SHA-256/标识符去重。 | 幂等键、超时重试查询和错误码尚未抽象为所有工具的统一接口契约。 |

### 面试回答

> 我会把工具设计成受控的业务 API，而不是给 Agent 一个万能函数。Lab Agent 中，知识问答、文献导入和报销动作职责分离；HTTP 层用 Pydantic 限制字段、长度和范围，报销服务再做策略校验。所有权限、ACL、危险参数和引用合法性都在服务端验证，`validate_tool_arguments()` 会拒绝路径穿越、Shell/SQL 片段和超大输入，模型不能拼命令执行。
>
> 报销接口还体现了副作用建模：preview 明确返回规范化参数、金额、币种、`draft_hash` 和 `external_write: true`，之后必须经过独立审批和幂等 confirm；知识问答则返回结构化 SSE 事件和引用。当前项目仍有两点不足：内部检索 plan 不是完整 JSON Schema，错误响应也没有统一稳定 code/retryable/trace_id。生产化时我会建立 tool manifest，为每个工具声明输入/输出 schema、权限、side effects、超时、幂等策略和错误码，模型只能调用白名单中的结构化工具。

### 追问与回答

1. 为什么不能给模型一个通用 `run_sql` 或 `run_shell` 工具？
   回答：这会把数据访问、文件系统和命令执行权限交给不可信自然语言输出，提示注入或参数错误即可造成数据泄露、破坏或远程执行。应暴露窄职责工具，例如“搜索当前项目授权证据”，并在服务端固定查询和资源范围。
2. 哪些参数应放在 JSON Schema 中，哪些必须由服务端策略二次校验？
   回答：字段类型、必填性、枚举、长度、数值范围和对象结构放入 schema；身份、项目可见性、ACL、当前状态、预算、来源 allowlist、业务阈值、审批与幂等必须由服务端从权威数据二次校验。schema 不能表达所有动态业务规则。
3. `retryable`、错误码和 HTTP 状态码之间如何分工？
   回答：HTTP 状态码说明协议层结果，如 401、403、422、429、503；稳定错误码说明业务类别，如 `AUTHZ_DENIED` 或 `BUDGET_EXHAUSTED`；`retryable` 则是调度决策，结合幂等性、`Retry-After` 和当前状态决定是否重试。
4. 读工具、知识库写入工具和外部支付工具的副作用标记应如何区分？
   回答：读工具标为 `read_only`，可缓存但仍受 ACL；知识库写入标为 `internal_write`，要求来源、去重和可能的用户确认；支付/报销标为 `external_write`，要求 preview、审批、版本绑定、幂等和外部回执。风险标签应驱动授权、审计和 HITL。
5. 如何让工具 schema 演进而不破坏已有 Agent 计划和审计回放？
   回答：工具声明携带稳定名称和版本，新版本使用兼容字段或新名称；执行记录保存当时的 schema/version 与规范化参数。回放使用旧适配器或受控迁移函数，绝不让新 schema 静默改变历史动作语义。
