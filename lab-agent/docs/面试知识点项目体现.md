## Agent、聊天、RAG 与工作流的边界

**通用结论：** 聊天重生成；RAG 重检索证据；工作流重预定义步骤；Agent 允许模型在受控范围内选择工具或分支。固定流程优先工作流。

### 当前项目中的体现

| 概念 | 当前项目中的体现 | 是否依赖模型自主决策 |
| --- | --- | --- |
| 聊天 | 网页“知识问答”输入框与 `/v1/chat/stream` SSE 接口 | 否。它是聊天式交互层；当前后端是确定性检索与返回，不是自由生成式对话。 |
| RAG | `LocalArchive` 与 `KnowledgeService`：解析、chunk、ACL-first 检索、hash-v1 向量/关键词排序、引用校验 | 否。它的职责是找已授权证据，回答只能引用本轮候选 chunk。 |
| 工作流 | `ManuscriptWorkflow` 的检索计划审核、证据表、草稿、人工审核状态机；`LocalAdminAdapter` 的 preview、审批、commit | 否。状态和转移由代码预定义，适合论文审核和报销等有合规步骤的任务。 |
| Agent | 研究方向助手把用户方向转为受控 Europe PMC 查询并入库；项目也预留模型接入位置 | 部分。当前是受控工具编排基础，不是模型自由选择工具的完整 Agent。 |

### 面试回答

> 这个项目里我没有把所有能力都叫 Agent。网页聊天只是交互层；RAG 是受 ACL 约束的证据检索能力；论文和报销属于步骤与审批固定的业务，所以我用显式状态机工作流实现。当前 Agent 成分主要体现在受控的研究方向导入和工具边界设计上，但还没有接入 LLM 规划器，因此不能声称模型会自由选择工具或自主编排。
>
> 这体现了“固定流程优先工作流”：报销不能让模型决定是否跳过审批，论文审核不能让模型跳过人工复核；模型只适合处理方向理解、检索式生成和基于授权证据的总结。后续接入模型时，它只能在服务端限定的工具集合内选择，例如检索已授权知识或生成候选检索式，审批、提交和权限判断仍由确定性工作流负责。

## 什么时候不该用 Agent

**通用结论：** 当步骤已经固定、结果需要严格复现、存在高风险外部写入，或模型没有带来有效决策增益时，不应把控制权交给自由规划 Agent。这类能力应由确定性服务、规则引擎或显式状态机执行；模型至多提出候选内容，不能绕过校验、权限和审批。

### 当前项目中的体现

| 场景 | 为什么不使用自由 Agent | 当前确定性实现 |
| --- | --- | --- |
| 报销审批与提交 | 提交会产生外部业务影响，必须防止超额、自己审批、草稿被篡改后继续提交和重复提交。模型不能决定是否跳过这些门禁。 | `LocalAdminAdapter` 先按策略生成 preview，再创建 `pending_approval` 任务；提交时校验精确的 `draft_hash`、非申请人审批和幂等键。当前是 SQLite 本地模拟器，不是真实财务 API。 |
| 论文撰写流程的状态流转 | 检索计划审核、证据核对和人工复核是合规与可追溯要求，不能让模型自行跳过。 | `ManuscriptWorkflow` 用显式状态机依次流转 `draft -> search_plan_review -> retrieve -> ingest -> relevance_review -> evidence_table -> manuscript_draft -> human_review -> completed`，并持久化 checkpoint、预算和截止时间约束。 |
| 权限与检索范围 | 用户能否读取某篇文献是安全规则，不是语言理解问题；模型不应根据提示词判断权限。 | `authz.py` 和 `LocalArchive` 在排序前执行 active user、项目角色和文档 ACL 判断，形成 ACL-first retrieval。 |
| 文献下载、解析与入库 | 这是典型 ETL：文件格式、体积、安全、去重、来源和授权状态必须一致、可审计、可重跑。 | `ingestion.py` 与 `LocalArchive` 固定执行类型/大小检查、可执行文件头拒绝、JATS 解析、SHA-256 和标识符去重、来源与许可证记录；开放获取导入只接受有全文的合规来源。 |
| 发布门禁与工具参数校验 | 路径穿越、Shell/SQL 片段和超长输入属于安全边界，不能由 Agent "酌情放行"。 | `release_gate.py` 以规则拒绝危险参数，并对审批草稿、checkpoint 和预算等条件进行确定性验证。 |

### 面试回答

> 在 Lab Agent 中，我刻意没有把所有流程都做成自由 Agent。凡是模型决策不会增加价值、但错误代价很高的地方，都写成确定性服务或状态机：报销提交需要策略校验、他人审批和幂等；论文工作流需要固定审核节点与 checkpoint；ACL 和文献入库则必须先保证权限、来源、去重和可复现性。
>
> 模型更适合处理低风险且不确定性高的部分，例如理解研究方向、生成候选检索式，或在已授权证据上做总结。即使后续接入 LLM，服务端仍必须掌握权限判断、审批、提交、预算、输入安全和审计；模型不能自行决定跳过这些门禁。当前项目的研究方向助手也仍是受控术语扩展或英文关键词处理，尚未配置 LLM 规划器，因此我会如实把它定位为 Agent 化边界的基础，而不是已实现的自由规划 Agent。

## 单 Agent、图工作流、多 Agent 如何选

**通用结论：** 默认先选单 Agent 或图工作流。任务只需要一次受控的理解、检索或总结时，单 Agent 的上下文和成本最简单；有审批、状态、重试、预算限制和人工接管时，用图工作流显式建模节点与转移。只有角色天然分工、各自产物可验证、且隔离上下文确有收益时，才引入多 Agent；否则会增加协调成本、状态不一致和调试难度。

### 当前项目中的体现

| 方案 | 当前项目采用情况 | 项目依据与取舍 |
| --- | --- | --- |
| 单 Agent | 只具备受控单次任务的基础，尚未接入 LLM Agent。 | 研究方向导入由 `literature_import.py` 将方向转为受限 Europe PMC 查询，知识问答则由检索服务返回已授权证据。当前不需要多个模型角色相互协作；即使后续接入模型，也应先让一个模型在工具白名单内完成候选检索式或证据总结。 |
| 图工作流 | 已采用“图式状态机”思想，是项目处理复杂流程的主方案。 | `ManuscriptWorkflow` 定义固定状态和合法边：检索计划审核后才能检索，证据表后才能起草，最后必须人工审核。workflow、checkpoint、预算、deadline 与 `failed/cancelled` 终态被持久化，因此可恢复、可审计并能拒绝非法跳转。实现是自定义 SQLite 状态机，不是 LangGraph 等图编排框架。 |
| 多 Agent | 当前未实现，也不应为了“看起来更智能”而加入。 | 项目中的检索、入库、权限、审批和起草步骤存在严格前后依赖，并且核心产物必须落库、受 ACL 保护、可验证。拆成“检索 Agent、写作 Agent、审核 Agent”会引入上下文传递、证据一致性和权限扩散问题，但没有带来足够收益。 |
| 人类角色协作 | 已实现，但不是多 Agent。 | PI/reviewer 审核检索计划与论文，finance approver 审批报销；这是权限隔离的人机协作，决策主体是明确的人和确定性服务，而非多个模型实例。 |

### 面试回答

> 我在 Lab Agent 里没有默认上多 Agent。简单的研究方向导入和知识问答只需要受控检索与处理，单个受限执行单元就足够；真正复杂的是论文产出和报销审批，它们的难点是状态、审批、预算和审计，所以我用显式状态机建模成图式工作流。
>
> 例如论文流程必须从 `draft` 经检索计划审核、检索、入库、证据表、草稿到人工审核，代码只允许合法转移，并保存 checkpoint，以便失败后定位和恢复。项目当前没有 LangGraph 或多 Agent 编排框架，也没有并行分支；这是有意的范围控制。若未来需要多 Agent，我只会在角色边界天然清楚且输出能自动验证的场景引入，例如一个受限检索规划角色生成候选查询、一个证据校验角色验证引用；但二者都只能读取已授权内容，最终入库、审批和状态推进仍由确定性服务负责。

## ReAct 的优缺点

**通用结论：** ReAct 将“推理（Reason）-行动（Act）-观察（Observe）”串成闭环：模型根据当前信息选择工具，读取观察结果后继续调整，适合检索、排错和开放式探索。它的代价是模型可能重复调用、走偏或陷入长循环，轨迹更长、成本更高、结果也较难稳定复现。因此生产实现不能只靠提示词要求模型“谨慎”，而应把动作结构化、限制步数和预算、持久化状态与审计，并将危险操作交由确定性门禁处理。

### 当前项目中的体现

| ReAct 要素或风险 | 当前项目中的实现 | 应如实说明的边界 |
| --- | --- | --- |
| 推理-行动-观察的适用场景 | 研究方向导入、受 ACL 约束的文献检索、证据表构建是未来可由 ReAct 辅助的探索性环节。 | 当前没有接入 LLM 规划器，也没有运行中的 Reason-Act-Observe 模型循环；方向助手是受控术语扩展或英文关键词处理。 |
| 结构化行动 | 论文流程被拆成 `set_search_plan`、`approve_search_plan`、`retrieve`、`ingest_retrieved`、`create_relevance_cards`、`build_evidence_table` 和 `draft_manuscript` 等显式服务动作。 | 这些动作由 CLI/API 或工作流调用，而非模型自行生成任意函数调用；这是未来接入 ReAct 时可复用的工具边界。 |
| 循环失控与成本 | `ManuscriptWorkflow` 的 `max_steps`、`max_tokens`、`max_cost_cents` 和 deadline 在每次受计量执行前检查，超限后进入 `failed`。 | 当前确定性流程里的 token/cost 增量为零，并未真实统计 LLM 调用费用；预算控制机制已经具备，但尚未接入模型计费数据。 |
| 轨迹难追踪、难恢复 | 每次状态推进写入 SQLite checkpoint；`GovernanceStore` 定义了 request/trace、工具、参数摘要、检索文档、耗时、成本和最终状态等审计字段。 | checkpoint 已用于论文工作流；治理存储是本地实现/契约，不能声称已覆盖所有网页请求或完整模型思维链。 |
| 危险行动与错误观察 | 检索始终 ACL-first，工具参数由 `validate_tool_arguments()` 做路径穿越、Shell/SQL 片段和大小校验；报销还要求审批与幂等提交。 | ReAct 即使将来接入，也只能请求这些受限工具，不能直接读越权数据、拼接命令或绕过审批。 |

### 面试回答

> ReAct 的优势是探索性强：模型可以先形成检索假设，调用工具观察结果，再决定下一步。它的问题也正来自这个循环，模型可能反复检索、错误地把一次观察当结论，导致轨迹变长、成本失控且不易复现。
>
> Lab Agent 当前没有把 ReAct 直接跑进生产路径，而是先实现了它需要的外部护栏。论文流程将每一步固化为结构化动作，用显式状态机限制合法顺序；每次受计量执行检查步数、token、成本和 deadline，并持久化 checkpoint。检索前先过 ACL，工具参数和报销写入还要经过确定性安全与审批门禁。后续若接入 ReAct，我会让模型只产生候选搜索计划或调用受限检索/总结工具，服务端记录每次工具调用的输入摘要、证据和结果；达到预算或没有新增证据时终止，而不是让模型自由循环。

### 代码证据与真实边界

| 主题 | 代码或接口 | 面试中应强调的设计价值与边界 |
| --- | --- | --- |
| 结构化动作与状态 | `app/services/manuscript_workflow.py` | 状态机动作有前置状态校验，避免 ReAct 式循环越级跳转；当前不是模型驱动循环。 |
| 终止条件 | `ManuscriptWorkflow._consume()`、`app/services/release_gate.py` 的 `BudgetController` | 分别限制步数、token、成本和时间；需接入真实模型用量后才能成为完整成本控制。 |
| 轨迹与恢复 | `checkpoints` 表、`resume()`、`CheckpointStore` | 保存业务状态和动作结果，支持审计/恢复；不保存或展示模型隐藏推理链。 |
| 审计契约 | `app/services/governance.py` 的 `AuditEvent`、`GovernanceStore` | 可记录 trace、工具版本、参数摘要、检索文档和最终状态，并对敏感内容脱敏；当前为本地 SQLite 参考实现。 |
| 工具安全与观测约束 | `app/services/release_gate.py`、`app/services/local_archive.py` | 对工具参数与权限做服务端验证，且只能基于已授权检索结果构建证据。 |

## planning 怎么落地

**通用结论：** Planning 不应只是模型输出的一段自然语言，而应成为可校验、可持久化的数据结构。至少要记录目标、子任务/依赖、允许使用的工具、成功条件、当前状态和预算。执行器根据计划和状态推进；当结果不满足成功条件时，可以生成新的候选计划，但固定子流程和高风险节点仍应由代码与审批门禁控制，不能每轮都让模型从头决定全部步骤。

### 当前项目中的体现

| planning 要素 | 当前项目实现 | 真实边界或改进方向 |
| --- | --- | --- |

### 面试回答

> 我在 Lab Agent 中把 planning 落在可持久化的数据和状态机上，而不是让模型每轮重新思考流程。论文工作流创建时保存研究问题和预算；检索计划以 JSON 保存，至少包含 query、sources、inclusion、exclusion，并在进入检索前经过 reviewer 审批。后续检索、入库、证据表、草稿和人工审核由固定状态依赖推进，每一步都写 checkpoint。

## Agent state 包含什么

**通用结论：** Agent state 是任务在可恢复执行过程中需要的最小、可信上下文，不等同于把所有数据都塞进一张表。应包含任务/用户/租户或项目标识、目标和计划、当前步骤及状态、受限工具调用和结果引用、审批决定、错误、预算、最终状态与 schema/计划版本。大文件、全文、附件和完整工具返回应放对象存储或业务库，state 仅保存不可变 ID、哈希、摘要和必要的定位信息；这样更利于恢复、审计、权限控制和成本管理。

| --- | --- | --- |

## 终止条件如何定义

**通用结论：** 终止条件应先定义为可观察的状态，而不是“模型说任务完成”。至少区分成功、失败、取消和预算耗尽；同时设置最大步骤、token/成本、deadline，以及针对 Agent 循环的重复 state/重复工具调用检测。成功必须由可验证产物和必要审批决定。终止原因、最后状态和证据应持久化，避免重试后继续错误执行或重复外部写入。

### 当前项目中的体现

| 终止类型或护栏 | 当前项目实现 | 真实边界或改进方向 |
| --- | --- | --- |
| 成功 `completed` | 论文工作流只有在 `human_review` 阶段由非空 reviewer 调用 `complete_human_review(..., approved=True)` 后才进入 `completed`。此前必须已形成检索结果、证据表和草稿。 | 成功依赖确定性前置产物和人工审核，符合“可验证产物”原则；当前没有自动质量评分或引用完整性阈值。 |
| 业务失败 `failed` | 人工审核不通过会从 `human_review` 转为 `failed`；预算耗尽也会写入 `failed` 和 `budget_reason`。 | 非预算异常没有统一终态处理：例如无授权检索结果时 `ingest_retrieved()` 抛出 `WorkflowError`，但不会自动把 workflow 更新为 `failed`。 |
| 取消 `cancelled` | `cancel(workflow_id, reason)` 可在非终态中写入 `cancelled` 和原因；报销任务也只允许在 `pending_approval` 状态取消。 | 这是服务层能力；当前 CLI 的 workflow `advance` 动作未暴露 cancel，网页端取消体验/取消传播尚需补齐。 |
| 最大步骤、token、成本与 deadline | `_consume()` 和 `BudgetController.consume()` 分别检查 `max_steps`、`max_tokens`、`max_cost_cents` 和 `deadline_epoch`。任一越限会停止后续调用。 | workflow 当前仅在 `retrieve()` 前调用 `_consume()`，且 token/cost 增量是 0；接入 LLM/API 后应在每次模型/工具调用前后统一计量。 |
| 非法状态与重复执行 | 各动作通过 `_require_state()` 限制只能从预期状态推进；终态 workflow 无法再取消，证据表/相关性卡用唯一约束减少重复行。报销提交使用幂等键防止重复外部写入。 | 不存在通用“重复 state/重复观察”检测，例如连续相同查询、相同工具参数或相同状态摘要达到阈值后的自动停止。该能力对未来 ReAct 循环仍需补充。 |
| 可追溯终止 | 状态转移及预算失败写入 checkpoint，`resume()` 可返回最后状态和预算原因；治理契约还预留 `final_state`、`error_code` 和 trace。 | 当前 checkpoint 可用于恢复和审计，但还未形成统一的终止原因枚举、完整重试策略与全链路事件写入。 |

### 面试回答

> 在 Lab Agent 中，我把终止定义成状态机的可验证终态，而不是让模型自行宣布完成。论文只有在已经产出授权检索证据、证据表和草稿，并且 reviewer 明确批准后，才能进入 `completed`；审核拒绝进入 `failed`，用户或系统也可以显式进入 `cancelled`。每一步还受到最大步骤、token、成本和 deadline 的约束，超限会记录 `budget_reason` 并停止。

## 如何处理工具失败

**通用结论：** 先按失败类型分类，而不是笼统地“重试”。网络超时、临时 5xx 和限流可以在固定次数内退避重试；结构/schema 错误应返回机器可读错误，并只允许模型进行有限次结构化修正；权限拒绝、危险参数、审批冲突和重复外部写入属于不可重试或需人工处理的失败，必须直接停止。每个工具都应明确超时、重试次数/退避、幂等键、错误码、审计和最终状态。

### 当前项目中的体现

| 失败类型 | 当前项目实现 | 真实边界或改进方向 |
| --- | --- | --- |
| 网络超时与单篇下载失败 | Europe PMC 搜索使用 30 秒 timeout，全文下载使用 60 秒 timeout；全文下载、文件写入或 JATS 解析失败会写进 `skipped.jsonl`，继续处理下一篇。 | 未实现固定次数重试、指数退避、429/`Retry-After` 处理或连接错误分类；搜索请求本身失败会直接向上抛出。 |
| 可用文献不足 | 如果符合开放获取和全文要求的候选不足，或最终可用下载数不足目标，导入抛出 `RuntimeError` 并给出 manifest/skipped 文件位置。 | 这是明确失败，不会自动换查询或降低标准；后续可让用户/受控规划器提交新计划，但不应悄悄扩大来源或放松开放获取条件。 |
| schema/参数错误 | `set_search_plan()` 校验计划必填字段；Pydantic 模型校验 API 输入；报销草稿要求字段集合完全匹配、金额/币种/收据满足策略。 | 目前错误以 `ValueError`/`AdapterError` 或 HTTP 422/403 返回，没有面向 LLM 的统一 JSON Schema 错误码，也没有“一次结构化修正”编排。 |
| 权限与危险操作 | 用户、项目角色和 ACL 不满足时直接拒绝；`validate_tool_arguments()` 拒绝路径穿越、Shell/SQL 片段和超大参数；引用必须属于已授权检索结果。 | 正确策略是停或转人工，不能让模型通过修改措辞绕过；当前 API 将多类 `AdapterError` 统一映射为 403，错误语义仍可细化。 |
| 业务冲突与审批失败 | 报销提交必须匹配原始 `draft_hash`、有效的非申请人审批和 idempotency key；重复键或冲突键会被拒绝。 | 当前是本地 SQLite 模拟器，未处理真实外部系统的超时后“是否已提交”查询与补偿事务。 |
| 重复执行与可恢复性 | 文献按 SHA-256/标识符去重，证据记录有唯一约束，工作流和审批任务有 checkpoint/audit；`IdempotencyGate` 和数据库唯一键防止同一报销重复提交。 | 工作流缺少统一的重试次数、退避调度、错误分类和失败转移策略；部分业务异常只抛错而未进入 `failed`。 |

### 面试回答

> 我会将工具失败分为可重试和不可重试两类。在 Lab Agent 的文献导入中，网络调用有 30/60 秒超时，单篇下载或解析异常会记录到 `skipped.jsonl` 并继续批次，避免一篇坏文献阻塞整个任务；如果最终可用数量不足，则明确失败，不会静默降低开放获取或全文校验标准。当前没有指数退避、429 处理和搜索请求重试，这是生产化前需要补的。
>
> 对 schema、权限和高风险写入，我不让 Agent 自由猜测。检索计划、API 输入和报销字段都由代码校验；ACL、危险参数、审批冲突直接停止。报销通过 draft hash、审批和 idempotency key 保证重试不会变成重复提交。后续接入 LLM 时，我只会针对可修复的结构错误返回标准化字段错误并允许一次受限修正；网络错误采用有上限的退避重试；权限、危险操作和业务冲突直接转人工或结束，并写入统一错误码和审计记录。

## 如何防止死循环

**通用结论：** 防止死循环必须依赖服务端状态和预算，不能仅靠提示词。至少包括全局步骤/token/成本上限、每个工具的重试上限、节点与工作流 deadline、状态或工具调用指纹、以及“无新增证据/无状态进展”的判定。超过任一上限时，必须写明停止原因并进入失败、等待澄清或人工接管；高风险外部写入还需幂等保证，避免重试变成重复执行。

### 当前项目中的体现

| 护栏 | 当前项目实现 | 真实边界或改进方向 |
| --- | --- | --- |
| 全局步骤与预算上限 | `workflows` 保存 `max_steps`、`max_tokens`、`max_cost_cents` 及实时计数；`_consume()` 和 `BudgetController.consume()` 在调用前检查，超限后拒绝继续。 | 工作流当前只在 `retrieve()` 前消耗一次步骤，token/cost 增量为 0；接入模型和外部工具后应让每一次调用统一计量。 |
| 工作流 deadline | `create()` 保存 `deadline_epoch`，默认一小时；`_consume()` 发现超时将 state 写为 `failed`，并记录 `budget_reason="deadline"`。 | 只有工作流级 deadline，没有检索、下载、审批等节点级 deadline 或取消信号传播。网络下载虽有 30/60 秒 timeout，但不是统一节点调度机制。 |
| 固定状态图 | 论文流程为单向显式状态机，动作先经 `_require_state()` 验证；终态 `completed/failed/cancelled` 不能再取消。 | 这能防止非法状态回跳，但本身不是对自由 Agent 循环的重复 state 检测；`NEXT_STATE` 是静态定义，当前没有动态重规划回边。 |
| 检查点与停止原因 | 每次状态转移写 checkpoint；预算耗尽时额外写 `failed` checkpoint 和具体原因。治理 `AuditEvent` 还定义了 trace、error code 和 final state。 | checkpoint 已在工作流使用；`GovernanceStore` 是本地审计契约，尚未确认所有 API/工具调用都已自动写入。 |
| 工具重复与副作用控制 | 文献入库按 SHA-256/标识符去重，证据卡/表有唯一约束；报销创建和提交通过 idempotency key 防止重复外部写入。 | 没有“同一工具 + 规范化参数”的重试计数，也没有相同查询/相同结果哈希达到阈值后的自动停止。 |

### 面试回答

> 在 Lab Agent 中，我先用确定性结构减少循环空间。论文流程不是自由回环，而是固定状态机；每一步要满足前置状态，状态转移会持久化 checkpoint。执行还受最大步骤、token、成本和全局 deadline 限制，超限时写入 `failed` 与具体 `budget_reason`，因此不是简单地停止而无法解释原因。对于有副作用的报销操作，再叠加 idempotency key、审批和草稿哈希，防止重试造成重复提交。
>
> 但我不会夸大当前能力：它尚未运行自由 ReAct 循环，所以没有同工具重试上限、state hash 或无进展检测。若接入 Agent，我会对 `workflow_id + node + tool_name + 规范化参数 + 上次结果哈希` 计算指纹，记录连续重复次数；相同调用超过上限，或连续 N 轮没有新增授权文档、证据行或状态变化时，停止并标记 `no_progress`，再要求用户澄清或转 reviewer。每个停止事件都写入 trace、预算快照、最后工具结果摘要和原因，便于恢复与排障。

## HITL 放在哪

**通用结论：** HITL（Human in the Loop）应放在不可逆、高影响或需要专业责任归属的边界之前，而不是把人工插在每个低风险步骤中。典型节点包括发送对外消息、创建正式工单、修改生产数据、支付/报销、删除和设备控制。审批界面或审批记录必须能让人看清：谁发起、参数是什么、影响范围、数据/证据来源、审批的具体版本、可选的批准/拒绝/取消动作，以及提交后的审计 ID。

### 当前项目中的体现

| HITL 位置 | 当前项目实现 | 审批展示/校验内容 | 真实边界或改进方向 |
| --- | --- | --- | --- |
| 检索计划执行前 | `set_search_plan()` 将计划置为 `search_plan_review`，只有 `approve_search_plan(workflow_id, reviewer_id)` 后才能进入 `retrieve`。 | plan 必须包含 query、sources、inclusion、exclusion；checkpoint 记录计划和 reviewer ID。 | 这是服务/CLI 的人工节点，当前没有独立的网页审核工作台、审批意见或 reviewer 角色/利益冲突校验。 |
| 论文完成前 | 证据表和草稿完成后进入 `human_review`；`complete_human_review(..., approved=True)` 才能进入 `completed`，拒绝则 `failed`。 | 草稿中的证据以 `document_id:chunk_id` 定位，证据表关联 document/chunk；checkpoint 记录 reviewer 和决定。 | reviewer 只校验非空字符串，未接入项目角色、双人复核、评语、版本锁定或电子签名。 |
| 报销外部提交前 | `preview_submission -> create_approval_task -> record_approval -> submit_approved_request` 是显式的 preview/approve/commit 流程。 | preview 返回规范化 payload、`draft_hash`、金额、币种和 `external_write: true`；提交时校验审批人角色、非申请人审批、审批有效期、精确 draft hash 和 idempotency key。 | 当前 `external_requests` 是 SQLite 中的本地模拟，不会真实付款；真实财务集成还需展示收款方、税务/凭证、政策依据、外部系统回执和补偿语义。 |
| 取消窗口 | `pending_approval` 报销任务可取消，论文 workflow 在非终态可 `cancel(reason)`。 | 审计记录任务取消或 checkpoint 原因，防止待审批任务继续被误提交。 | 缺少面向长时间运行任务的取消信号传播、通知和审批超时升级。 |

### 面试回答

> 我把 HITL 放在影响边界，而不是每一次检索上。Lab Agent 中，检索计划必须先由 reviewer 批准才能执行；论文必须经过人工审核才能从 `human_review` 进入 `completed`；最典型的是报销，系统先生成 preview，再创建待审批任务，由具备 finance-approver 角色且不是申请人的人审批，最后才允许带幂等键的 confirm 提交。

> 报销审批并不是只显示“是否确认”，而是绑定规范化请求、金额、币种、外部写入影响和 `draft_hash`。提交时再次校验审批对应的是同一版本，避免人审 A、系统提交 B；审批、提交和取消也会留下审计记录。当前外部提交是本地 SQLite 模拟器，论文 reviewer 也未做角色/双人复核校验，文献批量导入只有角色控制而没有二次确认。这些都是教学版的真实边界；生产化时我会按影响等级补齐审批工作台、证据/来源展示、角色分离、审批意见、过期与撤销、通知升级和真实外部回执。

## 如何度量自治

**通用结论：** 自治程度不是“模型调用次数越少越高”，而是系统在授权范围内可靠完成任务，并在不该继续时安全停止。指标至少应同时覆盖：任务成功与质量、工具正确率、人工接管/审批、失败安全性、成本、时延和返工率。对高风险任务，正确拒绝越权、危险或证据不足请求同样是成功；必须把“安全拒绝”与“无理由失败”区分开来。

### 当前项目中的体现

| 指标维度 | 当前项目已有基础 | 真实边界与建议的统计口径 |
| --- | --- | --- |

| 成本与时延 | `AuditEvent` 预留 `latency_ms`、`estimated_cost_cents`、tool/version、trace 和 final state；workflow/governance 有步骤、token、成本预算字段。 | 当前未证明所有调用自动落审计，且未接入真实 LLM/API 用量。生产指标应至少看 p50/p95 时延、每成功任务成本、每工具成本和预算耗尽率。 |
| 返工与可恢复性 | workflow 有 checkpoint、`failed/cancelled` 状态和人工审核；入库记录 created/duplicates，报销有 idempotency。 | 没有返工率/重开率的聚合定义。可统计计划被拒后重提次数、论文草稿被拒后重开次数、相同文献重复导入率和审批后取消率。 |
| 分级上线 | `ROLLOUT_STAGES` 按只读知识、分析草稿、行政草稿、批准后的真实写入逐步提升权限，并要求 rollback。 | 目前是发布就绪报告中的策略检查，不是线上 A/B 或影子流量指标系统；后续应按阶段设定不同 SLO 与安全阈值。 |

### 面试回答

> 我不会只用“任务完成率”衡量 Agent 自治。Lab Agent 把自治拆成任务质量、工具正确性、人机协作、安全、成本和时延六类信号。当前已经有约 30 个知识问答评测 case，覆盖授权、引用、无证据和攻击输入；发布检查还会验证路径穿越、SQL/Shell 片段、超额报销等是否被正确拒绝。这里的拒绝不是失败，而是高风险任务的正确结果。
>
> 对复杂任务，我把成功定义为可验证产物和必要审批：论文需要证据表、草稿和 reviewer 批准，报销需要合法 preview、独立审批和幂等提交。项目还预留了 trace、工具版本、时延、估算成本和最终状态字段。当前不足是这些数据没有统一自动采集和看板，发布报告也只检查评测数量而不计算成功率。因此生产化时我会按任务风险分组，监控任务成功率、工具调用正确率、人工接管率、拒绝的 precision/recall、p95 时延、每成功任务成本和返工率；当安全拒绝变差或 false allow 上升时，即使完成率高也要降级或回滚。

### 追问准备

1. 为什么高风险任务应优先优化 false allow，而不是盲目提高完成率？
2. 如何区分“合理拒绝”“工具故障”“模型错误”和“人工主动取消”？
3. 人工接管率高时，如何判断是模型能力不足、流程设计过严还是风险策略正确？
4. 如何设计离线评测集、线上埋点和人工抽检，使三者互相校验？
5. 每成功任务成本应如何分摊检索、下载、模型、审批等待和重试成本？
