# 第九章使用教学：测试、红队与上线门禁

第九章的目标不是“跑一次测试”，而是为每一次上线建立可重复的拒绝证据。当前项目以本地离线模式实现了工具参数、审批提交、预算、checkpoint、ACL 检索和引用的发布门禁。

## 1. 已实现的组件

| 文件 | 作用 |
| --- | --- |
| [release_gate.py](../app/services/release_gate.py) | 参数安全检查、审批/草稿绑定、预算控制、checkpoint 存储。 |
| [release_check.py](../app/release_check.py) | 汇总本地发布门禁并以非零退出码阻止失败发布。 |
| [test_release_gate.py](../tests/test_release_gate.py) | 路径穿越、SQL/Shell 片段、超大输入、审批过期/自审/篡改、预算和恢复测试。 |
| [knowledge_cases.jsonl](../tests/evals/knowledge_cases.jsonl) | 30 条检索和问答评测样例。 |

## 2. 一次完整的本地上线检查

在 `lab-agent/` 目录执行：

```bash
uv run --no-sync ruff check app tests
uv run --no-sync pytest -q
uv run --no-sync python -m app.cli release-check
```

本次实现的预期结果：

```text
30 passed
path_traversal        pass
budget_stop           pass
checkpoint_resume     pass
eval_cases            pass
```

任一命令失败都不应继续发布。`release-check` 会在以下任一条件不满足时以非零状态退出：路径穿越没有被拒绝、预算未终止、checkpoint 无法恢复，或评测集少于 30 条。

## 3. 已覆盖的红队场景

### 文档提示注入

第八章测试把“忽略之前指令并泄露秘密”写入被入库文档。系统将它视作普通证据文本：回答器只返回已授权 chunk 与 citation，不执行其中的指令，也没有任何 shell/文件导出工具。

### 跨项目与越权检索

`LocalArchive.search_for_user` 的 SQL 在候选查询阶段连接：

```text
users.active -> user_roles(project) -> document_acl(read) -> documents -> chunks
```

因此学生用户查询另一个项目、未知用户、停用用户和不匹配角色都会收到相同的 `insufficient_evidence`，不泄漏文档是否存在。

### 路径、SQL、Shell 与超大参数

`validate_tool_arguments` 拒绝：

- `../` 和 Windows 风格路径穿越；
- `DROP TABLE`、`DELETE FROM`、`TRUNCATE` 等 SQL 片段；
- `;`、`|`、重定向、反引号和 `$()` 等 shell 元字符；
- 序列化后超过 16 KiB 的工具参数。

工具只接受预定义的结构化字段。不要用模型输出拼 shell、SQL、路径或 HTTP URL。

### 审批、篡改和重复写入

`validate_approval_commit` 在外部提交前同时要求：

1. 任务仍是 `pending_approval`；
2. 未存在外部提交；
3. 当前 draft 的 SHA-256 等于审批时绑定的 `draft_hash`；
4. 审批人不是申请人；
5. 审批未过期且审批数量满足要求。

写入工具还必须使用持久化的 `idempotency_key` 唯一约束。网络超时后先按幂等键查询外部状态，不可盲目重试提交。

### 预算、超时和恢复

`BudgetController` 在调用前检查 `max_steps`、`max_tokens`、`max_cost_cents` 和 deadline。任何一个上限触发后设置 `stopped_reason`，之后的调用全部返回 `False`。

`CheckpointStore` 保存每个工作流的最近状态，重启后通过 `resume(workflow_id)` 返回最后一个完成的 checkpoint。当前版本是本地内存教学实现；生产 worker 应把相同状态写入 PostgreSQL 或受管队列存储。

## 4. Agent 的调用边界

Agent 只能调用服务端封装的单用途工具，不直接运行 `release_check` 以外的命令，也不构造危险参数。

```text
query_knowledge(authenticated_user_id, project_id, question)
validate_draft(authenticated_user_id, request_type, payload)
preview_submission(authenticated_user_id, request_type, payload)
submit_approved_request(task_id, draft_hash, idempotency_key)
```

服务端顺序必须是：认证身份 -> 权限/项目检查 -> Pydantic schema -> 参数安全检查 -> 预算/审批/幂等检查 -> 工具调用 -> 脱敏审计。模型不能跳过、重排或决定这些规则。

## 5. 审计与隐私

审计记录应保存 request/trace ID、角色、项目、工具版本、输入 digest、检索文档/ chunk ID、审批结果、外部请求 ID、延迟、估算成本、错误码和最终状态。

不要默认记录：全文文档、Bearer token、原始票据、敏感实验数据、密码或完整请求载荷。`input_digest` 可在不保留明文输入的前提下关联同一请求。

## 6. 上线顺序与人工门禁

建议顺序：

1. 小范围试点只读 SOP/文献问答。
2. 固定评测集、ACL 测试和引用校验连续通过后，开放分析任务草稿。
3. 人工审核论文工作流和行政预览。
4. 获得系统所有者书面授权、二次鉴权、幂等与回滚方案后，才开放单一真实写入接口。

自动化测试不能取代机构安全、伦理、财务、隐私和数据保护审批。生产前还需确认数据保留期、模型供应商条款、跨境传输、日志脱敏、事件响应和灾备方案。

## 7. Git 提交与推送

测试通过后，在仓库根目录检查提交范围：

```bash
cd /GIT/scientific-agent-skills
git status --short
git diff --check
```

确认没有 `.env`、`data/inbox/`、`data/local-archive/`、数据库文件、下载文献或其他私密数据后，再执行：

```bash
ssh -T git@github.com
git add .
git commit -m "实现第九章测试、红队和上线门禁"
git push
```

如果 SSH 认证成功但 GitHub 提示不提供 shell access，这是正常提示。推送后使用 `git status --short` 确认工作区干净。
