# Agent 面试问题项目化回答

## 1. 什么是 Agent？结合你的项目说一下。

Agent 不是多轮聊天页面，而是模型在受限环境中，基于当前任务状态选择允许的动作，调用工具、读取观察结果，并在成功、失败或预算耗尽时结束的一套执行结构。它的工程重点是状态、动作空间、工具约束和可验证产物，而不是让模型拥有无限制的自主权。

我的 Lab Agent 项目按这个思路实现。`AgentService` 只向模型暴露两个无副作用工具：`search_authorized_evidence` 检索当前用户有权限读取的本地论文证据，`propose_literature_query` 根据研究方向生成候选 Europe PMC 检索式。模型不能下载论文、导入数据、修改 ACL、审批或执行任意命令；工具名称、参数长度和角色权限都由服务端重新校验。

为了避免 Agent 无限循环，工具调用最多三轮，并记录 `run_id`、已执行工具、是否使用模型和最终状态。这样一次回答可以追溯到具体工具和证据，而不是只得到一段无法解释的模型输出。

项目中我也区分了 Agent 与工作流。研究问题理解、授权证据检索、候选查询生成这些需要一定判断但风险较低的环节，可以由受限 Agent 处理；论文导入、入库、实验信息提取、论文草稿审核等有明确顺序或副作用的步骤，由 `ManuscriptWorkflow` 状态机推进。检索计划必须先审核，后续才能检索、入库、构建证据表、起草并进行人工审核；每一步都会写 checkpoint。论文导入还需要用户确认，避免模型将候选检索式直接变成外部下载行为。

因此，我的项目不是“模型自主完成所有科研工作”，而是受控单 Agent 与确定性工作流的组合：模型负责有限的理解和工具选择，服务端负责权限、状态、审计和高风险动作。当前工具集较小，尚未实现复杂动态规划或多 Agent 协作；生产化还需要补齐真实 token/成本计量、超时与重复调用检测、统一追踪和离线评测集。
